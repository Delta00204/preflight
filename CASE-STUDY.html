01The problem

Before you can promise a date, you have to know what is already built

A forward-deployed engineer leaves a discovery workshop with a capability list and one question standing between them and a commitment: how much of this already exists, and how much are we building from nothing?

Every downstream number depends on that split. A capability that maps to a documented vendor API is an integration. A capability with no public path is an engineering project. Confusing the two is how a six-week pilot becomes a six-month one, and the confusion is usually discovered in week three, not week one.

For the half that does exist, the cost is rarely writing the call. It is getting permission to make it: an OAuth application, customer admin consent, a security review, a DPA. That is the last mile, and the last mile is where forward-deployed work lives.

Both halves of that answer were computable on day one. The authorisation model of every candidate API is public; so is its absence. It went uncomputed because there was no programmatic path from “triage support tickets” to “here is what exists, here is what does not, and here is what each one demands of you.” Orbit closes that gap. Its integrate call returns a real AUTH section, and its silences are themselves informative. That is the wedge, and it is why this product can exist now and could not have six months ago.

02The motion

Where this sits, and where it does not

The forward-deployed motion runs roughly nine stages. Preflight is built for two of them.

1Qualification: size the opportunityAE + SA
2Discovery workshop: what should the agent dofeeds Preflight
3Technical scoping & SOW: effort, sequence, datePreflight
4Access, security review, procurementPreflight
5First vertical slice
6Demo and iterate with the customer
7Harden: auth, errors, evals, observability
8Production cutover
9Handover, enablement, expansion

Stages 3 and 4 are where the gap between a working prototype and a production deployment opens up, and where a commitment made on instinct becomes a date the team has to hit. A narrow slot, but the expensive one.

The stage-4 contribution is the one people underrate. A security review asks which third parties, what scopes, what data leaves the building. Preflight can answer that on day one instead of week three, which is often the difference between a review that runs in parallel with the build and one that blocks it.

It stays out of stages 5 onward. Once you are building, the constraint is no longer information. It is engineering, and a scoping instrument adds nothing.

03The build

A readiness assessment, not a search tool

Preflight takes a deployment brief in plain English and answers the scoping question first: what already exists, what does not, and what each surviving capability will cost you in permission. On the sample support-agent brief:

1/6no public path, build it
5/6integrable
3/6no security review needed
5vendors entering review

The first tile is the one that changes a SOW. One capability in six has no public path at all. That is not an integration line item but an engineering project, and finding it in week one rather than week three is most of the value here. The timeline follows from the split rather than the other way round.

For the five that are integrable, the report returns a phased plan, blocking findings, a catalogue security scan, and Anthropic tool-use schemas for whatever cleared. Three can ship without waiting on a security review; two cannot, and knowing which is which on day one is what lets the review run in parallel with the build instead of blocking it.

04Redlines

Five times the evidence contradicted the design

These are the actual corrections, in build order. Each one changed the product, and four of the five were caught by instrumentation rather than by inspection. The last surfaced during final verification, after I had already called the tool validated.

Revision 1 · API misuse

I was asking Orbit the wrong question

Believed
Pass the deployment goal as the task on every integrate call, so Orbit has full context.
Observed
Orbit replied FIT: Not at all and truncated the entire brief: no AUTH, no STEPS. It was correctly judging one email endpoint against a whole support-deflection programme.
Changed
Scope task to the single capability. More context was actively harmful, a result I would not have guessed.
Revision 2 · Silent under-estimate

Missing evidence became “no auth required”

Believed
A clean URL with no key parameter means an open endpoint.
Observed
Brevo’s email API scored 0 days. It needs an API key. My classifier had inferred “no auth” from absent evidence, the failure the tool exists to prevent.
Changed
The classifier is now asymmetric by design. NONE is returned only on an explicit Orbit statement; absence floors at API-key and raises AUTH_UNVERIFIED. Optimism is the one direction this tool must never fail in.
Revision 3 · Over-correction

A catalogue gap is not an internal system

Believed
If Orbit rejects every candidate, it is custom work.
Observed
“Open an issue in a GitHub repository” returned only GET endpoints, so every candidate was rejected, and my tool called GitHub a 60-day custom build. A worse error than the one I set out to fix.
Changed
New verdict: not in the public catalogue. Keep the vendor’s real auth tier, flag for manual verification. Orbit also emits a re-search hint on rejection, so the tool now follows it automatically before giving up.
Revision 4 · Goodhart

My strongest claim rested on an unstable signal, and my first fix cheated

Believed
A zero-result from Orbit proves no public API exists. This drove the headline 60-day critical path.
Observed
The same capability, phrased five ways, returned 0, 10, 10, 0, 10 results. The verdict was a function of wording, not of reality. Worse, the top hit for “internal wiki” was Wikimedia Foundation.
First fix
Re-probe with simplified paraphrases. This stripped the words “internal company”, and returned NONE, 0 days, no flags for an internal knowledge base. I had improved the metric by asking an easier question.
Changed
Internality markers (our, internal, in-house, proprietary) are never stripped. They are the capability. Any capability naming an internal system that resolves to a public vendor now raises a blocking INTERNAL_MISMATCH and is scoped as custom work. The headline number is back, for a sound reason instead of a fragile one.
Revision 5 · Same bug, different door

“No authentication” did not mean what I matched on

Believed
Revision 2 had closed the under-estimation hole: only an explicit Orbit statement can yield a zero-day verdict.
Observed
A cold-cache run scored Oracle Cloud object storage at 0 days. Orbit had said: “No authentication scheme is present in the supplied request or collection context. Provide any authentication required by the Oracle API separately.” That is the collection author omitting auth, not an open API. My regex matched the words “no authentication” and took the optimistic reading.
Changed
The classifier now separates undocumented (“scheme is not present”, “provide separately”) from open (“no authentication is required”). Contract-gated vendors can never score as no-auth. Oracle now reads 45 days with the auth flagged unverified, and two regression assertions pin the behaviour.
Lesson
A guard written against one phrasing is not a guard against the failure. This one survived three validation runs because every brief in the suite happened to use clearer wording. It took a capability I had never queried to expose it.
05Research

What the catalogue actually covers

Before trusting the tool I measured its dependency: 32 representative enterprise capabilities across eight domains, 320 candidate endpoints. A defect is a catalogued entry an engineer should not ship: a sandbox host, a malformed URL, or an embedded credential.

Finance42%
ITSM22%
HR18%
Data10%
Identity5%
CRM2%
Internal2%
Comms0%

Defect rate by domain, 40 candidates each. Overall 12.8%. Finance is the outlier because payment vendors publish sandbox collections. PayPal, Adyen and GoCardless all surfaced test hosts that would silently no-op in production.

The operational read for an FDE: the catalogue is strong where integration is easy and weakest exactly where the money and the risk are. Comms is clean and near-frictionless; Finance is both the most defect-prone and the most consequential to get wrong. Plan review effort accordingly rather than uniformly.

One catalogue entry carried a live-looking API key in its example URL. Preflight redacts any such value on sight and never renders it. The catalogue is user-published content, so example URLs are untrusted input.

06Rigour

The harness caught what review did not

Eighty-three assertions run against a live server across five deployment briefs. The most serious catch was a security defect I had written myself:

PagerDuty’s routing_key, a secret, was leaking into a generated agent tool schema. I had filtered secrets on the URL path but not on the brief-derived path.

A model must never be able to select its own credential. Secrets are now structurally excluded on every path, and an assertion enforces it. Every validation run so far has surfaced a real defect; none were found by reading the code.

The suite also had a blind spot it could not see. It exercised the API and never loaded the page, so a duplicate const in the browser bundle shipped a completely dead UI while all assertions passed. The harness now parses the inline script and checks every element it queries, and immediately caught a stale reference I had left behind.

GuardEnforces
NONE only on evidenceAuth burden can never be silently under-estimated

determinismThe same brief yields the same commitment
07Honesty

Measured and assumed are kept structurally separate

Every endpoint, authorisation model, gotcha, FIT verdict and coverage gap is real and reproduced unaltered: 131 live API calls, one fetch in the codebase, zero mocks. The day counts are not. The tier-to-calendar-day mapping is my estimate, and the headline is real evidence multiplied by an invented constant.

Rather than bury that, it is load-bearing in the design. Every conclusion carries a decision trace whose steps are typed evidence, inference or assumption with their source, and an assertion guarantees exactly one assumption per row. An FDE who is asked “why fifteen days?” in front of a customer can answer from the artefact.

The same discipline forced a smaller correction: my “unknown vendor” flag was firing on Xero, Deel and Shippo, all real companies. The flag now reads not on your approved vendor list, which is an honest claim about the customer’s allowlist rather than a claim about the vendor.

09Scope

What I chose not to build

Cost modelling. It is the most requested thing a tool like this could add, and Orbit carries no pricing data whatsoever. Building it would mean inventing numbers and presenting them beside real ones. I already have exactly one invented number and it is fully labelled; a second would corrupt the first.

Shipped instead, in priority order:

  • Vendor pinning: let the FDE supply the customer’s known stack, which retires most mis-resolution at its root rather than flagging it downstream
  • A real dependency graph: today’s critical path is max(days), which assumes perfect parallelism and therefore understates real timelines
  • Ranges over point estimates: OAuth at Slack is days, OAuth at Workday is months
  • Multi-resource briefs: Orbit accepts several endpoints per call and returns step threading; I send one, so I am leaving sequencing information on the table
10Limits

Where it is still weak

The obvious objection first. Enterprise agents mostly touch the customer’s own instances and internal systems, and no public catalogue contains those. So is this solving the easy fraction?

Partly, and the answer is the reason the framing in section 01 matters. The tool is not a directory lookup; its most valuable output is the boundary. Knowing that one capability in six has no public path, and that another resolved to a public vendor when the brief clearly named an internal system, is the scoping information a SOW turns on. Coverage gaps are not the tool’s blind spot. They are its subject.

What it cannot do is see the customer’s own tenant: their Zendesk instance, their SSO configuration, their data residency posture. An FDE walks out of the discovery workshop already knowing that stack, which is why vendor pinning is first on the roadmap: it closes the gap with information the engineer already has, rather than trying to infer it.

Precision tracks catalogue quality. For thinly covered capabilities Orbit returns a plausible-looking wrong endpoint rather than nothing. “Query application error metrics” resolved to Meta with a 100% fit score and no flags. The guards make most of these visible; they do not catch all of them.

This is a scoping instrument, not an autopilot. It is designed to make a human’s day-one conversation with a customer sharper and better evidenced, not to replace the engineer’s judgement about what their customer runs.
